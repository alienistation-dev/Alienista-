## Critical

1. **Hardcoded session-secret fallback** — `app/src/lib/env.ts:17`. `SESSION_SECRET || 'default-fallback-dev-secret-key-32b'`, no production guard. If the env var is missing in a deployment, anyone can sign an admin session for any tenant. Fix: throw at startup when unset or short in production. *Both, Verified.* Whether production sets it: **unknown**.
0. **Self-signup becomes an org admin over Storage (verified in repo).** The anon key is public; if hosted Auth signups are enabled (Supabase default), anyone can call `/auth/v1/signup`. `handle_new_user` (`001_initial_schema.sql:85-91`) inserts a profile with role and org taken from signup metadata, defaulting to `admin` in the first organization. Storage policies `student_avatars_admin_write/update/delete` (`001_initial_schema.sql:789-811`) authorize by `get_my_role() = 'admin'`, so that user can insert, overwrite or delete every student photo in the org — the photos officers use to confirm identity at scan time. Fix: drop the `on_auth_user_created` trigger (the app uses its own session cookies, not Supabase Auth) and disable signups in the dashboard. Exposure hinges on one setting: Authentication → "Allow new users to sign up" — **unknown**.
2. **`correct_semester_assessment` executable through PUBLIC** — precondition: the caller needs an assessment UUID and the org UUID, which officers can read (`getSemesterAssessmentsAction` allows officers) and outsiders cannot. Realistic abuse is an officer falsifying sanctions under an admin's ID. Treat as High. — `supabase/migrations/20260822033000_phase5_sanctions_and_phase6_security.sql:185` is `SECURITY DEFINER`, trusts caller-supplied org and actor IDs; line 252 revokes from `anon, authenticated` but never from `PUBLIC`, which keeps Postgres's default EXECUTE. The anon key is public (`NEXT_PUBLIC_SUPABASE_ANON_KEY`), so a browser can call the RPC through PostgREST. Fix: new migration `REVOKE ALL ... FROM PUBLIC`, switch to `SECURITY INVOKER`, audit every older function the same way. *Verified in source.* Live grants: **unknown** (check with `has_function_privilege('anon', ...)`).

## High — offline / PWA

12. **Root cause of "PWA has no CSS offline"** — `app/public/sw.js:3` precaches only `/login`, `/favicon.ico`, `/manifest.json`. The fetch handler (line 36) is network-first and **never writes responses to the cache**, so offline every CSS/JS/RSC request falls through to `caches.match('/login')` and gets HTML. *Verified; astra also ran the worker in memory.* Fix: cache-first for `/_next/static/*` (content-hashed, safe to cache forever) and write successful responses to the cache; navigation-only fallback to a self-contained offline page.
13. **Cached `/login` can hold another user's page** — `/login` redirects signed-in users (`src/proxy.ts:22`), so the precached fallback may be an authenticated page. *B.*
14. **SW activation deletes other caches** — `sw.js:19` deletes every cache not named `attendqr-shell-v1`, including the scanner avatar caches. *Verified.*
15. **IndexedDB upgrade deletes unsynced scans** — `lib/offline-db.ts:66` deletes every object store when the old version is lower. A scanner updated before syncing loses scans. *Verified.*
16. **Transient errors strand offline scans** — `actions/attendance.ts:60` reports DB/lookup failures as missing records, which the reconciler marks non-retryable. *Both.*
17. **Replay attributes scans to whoever syncs** — `actions/attendance.ts:130` records the syncing session user, not the capturing officer. *B.*
18. **Delayed valid scans rejected as EVENT_CLOSED** before capture time is evaluated — `actions/attendance.ts:79`. *B.*

## Perceived UI slowness (measured)

Evidence: production build of `feat/sprint-reconcile` with placeholder env (`npm run build`, exit 0), emitted chunks in `.next/static/chunks`, bundled docs in `node_modules/next/dist/docs`.

Not the cause:
- **Bundle size.** 1,185 KB raw JS across 28 chunks; per-page start is mainly the framework (react-dom 223 KB + two shared chunks 124/110 KB). The 361 KB chunk holding `html5-qrcode` is referenced by no page manifest, i.e. the camera decoder is lazy as intended.
- **Layout.** `(dashboard)/layout.tsx` does no database reads; `getEffectiveOrgId` returns the session's org without a query.

Likely causes, highest impact first:
1. **Every navigation is an uncached server round trip.** All 12 app routes are dynamic (`ƒ`), and for dynamic routes the client cache is "Off by default (`staleTimes.dynamic`)" (`docs/01-app/.../prefetching.md:62`). Each tab switch shows the skeleton, then waits for the server again, even for a page seen seconds ago. Fix: `experimental.staleTimes: { dynamic: 30 }` in `next.config.ts` (mutations already call `revalidatePath`, which clears it). Trade-off: a revisited page can be up to 30 s stale.
2. **Server region vs database region — unknown, possibly the largest factor.** No `vercel.json`, so functions run in Vercel's default `iad1` (US East) unless changed in the dashboard. If Supabase is in Singapore, every query from a Palawan user crosses the Pacific twice. Fix: set the function region to match Supabase (e.g. `sin1` for `ap-southeast-1`). Check both regions in the dashboards.
3. **Full page reloads after saves** — `window.location.reload()` in `assessments-view.tsx:13,18`, `sanctions-policy-editor.tsx:74`, `settings-view.tsx:160`, `student-table.tsx:356`. Re-downloads and re-renders the whole app after every save. Fix: drop the reload; the actions already `revalidatePath`, use `router.refresh()` where the view holds local state.
4. **QR generator badges** wait for avatar fetch + 400×640 canvas PNG export before showing the QR, up to 8 at once (`badge-card.tsx:42`, Reviewer B).
5. **Scanner event select prefetches every avatar** concurrently (`offline-db.ts:246`, Reviewer B) — competes with the scanner on slow phones.
6. `my-attendance` runs 4 sequential awaits; two independent reads could run together (Reviewer B).
7. Geist fonts preloaded but unused (`layout.tsx:6`).

Measurement caveat: the owner's local runs use `npm run dev`. Dev mode compiles each route on first visit with Turbopack, so first clicks there are slow regardless of the above. Judge speed on the deployed site or `npm run build && npm start`.
